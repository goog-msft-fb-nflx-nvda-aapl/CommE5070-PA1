### Required experiment — Task 1 year-regression / hierarchical framing (src/task1_ordinal.py)
- **Config**: reuses the already-cached MERT-v1-330M layer-4 embeddings (train/validation splits of Dataset A only, test excluded), same preprocessing as the winning flat-classifier config — StandardScaler (fit on train) → PCA(128, fit on train). No new extraction.
- **(a) Regression framing**: Ridge regression (GridSearchCV over alpha∈{0.1,1,10,100}, 5-fold StratifiedKFold CV on train, n_jobs=1) predicting decade-index 0-5 as a continuous target, prediction rounded to nearest int (clipped to [0,5]) for top1/accuracy comparison. Result: MAE(raw prediction)=1.060 decades, MAE(rounded)=1.030, **top1(after rounding)=0.273**, QWK=0.605 — **worse than flat 6-way classification on every metric** (flat: top1=0.462, MAE=0.947, QWK=0.621). A linear regression head doesn't capture the era-discriminative structure as well as a direct classification decision boundary here.
- **(b) Hierarchical framing**: coarse 3-way classifier grouping adjacent decade pairs ({1960s,1970s}/{1980s,1990s}/{2000s,2010s}, logreg + GridSearchCV C, 5-fold CV) → predicted-coarse-group-conditional fine 2-way classifier (separate logreg per group, trained only on that group's train rows) picks the specific decade within the group. Result: coarse-stage accuracy=0.689, **final top1=0.432** (slightly below flat's 0.462), **final MAE=0.939** (marginally better than flat's 0.947), **QWK=0.659 (better than flat's 0.621)**.
- **Takeaway for report**: flat 6-way classification remains the best top1 config, but the hierarchical framing makes measurably "smoother" errors — better ordinal agreement (QWK) and MAE despite slightly lower raw accuracy — meaning when hierarchical gets it wrong, it tends to land closer to the true decade (e.g. confusing within-group neighbors) rather than jumping across groups. Regression framing is the weakest of the three approaches on every axis tested; don't recommend it. Worth reporting all three side by side rather than picking only the "best" one, since they answer slightly different questions (top1 vs ordinal-closeness-of-errors).

### Required experiment — Audio Language Model track, Qwen2-Audio-7B-Instruct (src/alm_infer.py)
- **Critical bug caught during smoke-testing, before trusting any results**: the first end-to-end test produced a clean, plausible-looking output ("1970s") with NO error — but a stray warning ("Keyword argument `audios` is not a valid argument for this processor and will be ignored") turned out to mean the audio was silently never passed to the model at all (wrong kwarg name — Qwen2AudioProcessor expects `audio=`, singular, not `audios=`). Caught by inspecting the processor's actual call signature rather than trusting a clean-looking single output. Fixed the kwarg name, re-ran the same test — and it then correctly *errored* demanding 16kHz input (Whisper's feature extractor, Qwen2-Audio's audio tower, requires 16kHz; our dataset is natively 24kHz) — this error, once audio was genuinely flowing through, is itself confirmation the original silent-no-audio bug was real (an all-text-no-audio call would never have hit this validation). Added librosa 24kHz→16kHz resampling before the processor call. **Verification**: re-ran on 3 validation clips with known labels (1960s/1970s/1970s) — model correctly predicted all 3 exactly. Only trusted the pipeline after this positive-control check, not just absence-of-error.
- This is a strong argument for always including a small known-label sanity check before trusting any ALM/generative-eval pipeline's output, even when it runs without crashing — a silently-ignored kwarg produced a perfectly well-formed, plausible single-token answer with zero indication anything was wrong.
- **Second bug, caught after a full "successful" run**: the first complete pass used a one-hot pseudo-probability built from a single free-form generated answer as the "probs" array for top1/top3 scoring. Traced through `np.argsort` on a one-hot vector and confirmed this is degenerate for top-3: ties among the zero-probability classes break by array index, so top-3 always credited the predicted class plus whichever *lowest-index* classes happened to be tied at zero (for Dataset A, that systematically means 1960s/1970s get free credit whenever the true label lands there, regardless of what the model actually thinks). **Fixed** by adding teacher-forced label log-prob scoring (`score_candidates` in src/alm_infer.py): for each of the 6 candidate labels, concatenate the prompt + candidate tokens and read off the model's own token log-probabilities (single forward pass per candidate, no autoregressive generation needed) — this gives a genuine ranked distribution over all 6 classes. Verified on 3 known-label clips: sensible calibrated scores (e.g. close scores between adjacent, easily-confusable decades) before trusting it. Free-form generation is still used, separately, purely to measure the invalid-output rate (how often the model's natural-language answer fails to parse) — that part of the original design was fine.
- **Third bug, caught by a suspicious result**: with the scoring fix, `direct` scored top1=0.326/QWK=0.534 but `cot_then_answer` scored top1=0.227/QWK=0.109 — a gap large enough to be suspicious rather than just "the prompts differ." Root cause: `score_candidates` always scored a *bare* label immediately after the prompt, but `cot_then_answer` explicitly asks the model to reason first and answer in the format `Answer: <label>` — scoring a bare label right after that prompt asks the model something it was never asked to do (blurt the label with no reasoning), which isn't a fair test of what the prompt is actually eliciting. **Fixed** by giving each prompt its own `answer_prefix` (`""` for `direct`, `"Answer: "` for `cot_then_answer`) so teacher-forced scoring matches each prompt's own declared output format.
- **Config** (final): encoder=Qwen2-Audio-7B-Instruct (`Qwen/Qwen2-Audio-7B-Instruct`, Apache 2.0), audio resampled 24kHz→16kHz (Whisper audio-tower requirement) before the processor call, top1/top3/confusion computed from teacher-forced label log-prob scoring (format-matched per prompt), invalid_output_rate computed separately from free-form generation + regex/alias parsing (`parse_label`), evaluated on Dataset A validation split (132 clips), 2 prompt designs.
- **Final results** (results/alm/qwen2audio_A/{direct,cot_then_answer}_metrics.json), now a fair comparison:

| prompt | top1 | top3 | MAE (decades) | QWK | invalid rate |
|---|---|---|---|---|---|
| direct | 0.326 | 0.659 | 1.220 | 0.534 | 0.008 |
| cot_then_answer | 0.333 | 0.652 | 1.265 | 0.512 | 0.008 |

### Task 2: OOF-fitted, temperature-calibrated fusion — `src/af3_stack_oof.py`

### Task 1: CORAL ordinal head — `src/coral_ordinal.py`
Round 3's strongest cross-source-convergent recommendation (all 4 sources) for Task 1: a CORAL (Cao et al. 2019, arXiv:1901.07884) cumulative-link ordinal head — shared weight vector `w^T x`, per-threshold biases `b_k`, extended-binary targets, `P(y>k)=sigmoid(w^T x + b_k)` — trained on the same MuQ layer1 embeddings that are Task 1's established best frozen-probe features. Rank-consistency (monotonic `P(y>k)` in `k`) is **not hard-constrained** here, same practical relaxation the reference `coral-pytorch` implementation uses — checked directly rather than assumed: 0% violation rate on validation, so this wasn't the issue.

- **First comparison caught a design flaw before trusting the result**: initially compared CORAL (a linear head) against the established best-config classifier, which is an **SVM with an RBF kernel** — a capacity/nonlinearity mismatch, not a fair "ordinal vs nominal decision surface" test. Added a proper **capacity-matched comparison**: plain logistic regression (also linear) on the identical layer1 features.
- **Result, both comparisons — CORAL loses clearly and consistently**:
  - CORAL: top1=0.3182, top3=0.7424, MAE=1.18 decades, QWK=0.630
  - Linear nominal (logreg, capacity-matched): top1=0.5000, top3=0.8409, MAE=0.79, QWK=0.751 — **CORAL loses on every metric**, including the ordinal-specific ones (MAE, QWK) CORAL is supposed to be better at.
  - Established best (SVM): top1=0.5076 — same story.
  - Both comparisons significant: CORAL vs logreg p=0.0005, CORAL vs SVM p=0.0002 (McNemar), CIs exclude zero, all favoring the nominal classifier.
- **Verified this is a real effect, not a training bug**: swept 9 (epochs × lr) configurations (300/1000/3000 epochs × lr 0.001/0.01/0.1) — val accuracy stayed in a narrow 0.28-0.34 band throughout, never approaching logreg's 0.50, while train accuracy at the default config (0.565) already exceeds val accuracy (0.318) by 25pt — a genuine train/val generalization gap, not undertraining. More epochs/higher LR only pushed train loss lower (more overfit) without moving val accuracy.
- **Honest interpretation**: CORAL's single shared-direction weight vector (one linear projection reused across all K-1 thresholds) is a much more constrained decision surface than logistic regression's per-class weight vectors — here that constraint costs more in raw discriminative flexibility than it gains from encoding the ordinal structure. This directly contradicts all 4 round-3 research sources' top recommendation for Task 1 — reported as a genuine, verified negative result, not dismissed as a training artifact. ### MuFun (9B audio-text LLM) — `src/mufun_infer.py`, the last remaining round-3 optional item
`Yi3852/MuFun-Instruct` (arXiv:2508.01178), ChatGPT's round-3 pick for "most architecturally independent" new ALM candidate. Unlike every other ALM in this project (Qwen2-Audio, AF3, Music Flamingo — all standard `AutoProcessor`-based HF audio-chat models), MuFun is a custom TinyLLaVA-style multimodal architecture with its own `model.chat()`-only documented interface and no exposed teacher-forced-scoring path — required substantially more integration work than anything else tried this project.

**Five real, distinct bugs found and fixed, in order, each verified by re-running after the fix (not assumed)** — by far the deepest debugging chain this project has hit, documenting the full trail since it's genuinely instructive:
1. **Nested meta-device `from_pretrained` conflict**: MuFun's own `__init__` calls `WhisperForConditionalGeneration.from_pretrained(...)` for its internal audio tower *while already inside* the outer `from_pretrained`'s meta-device init context — current transformers refuses this nested call. Fixed by no-op-patching `transformers.integrations.accelerate.check_and_set_device_map`, the specific function that raises.
2. **`tie_weights()` signature mismatch**: MuFun's own `TinyLlavaForConditionalGeneration.tie_weights()` override predates kwargs (`recompute_mapping=`, `missing_keys=`) that current transformers now passes to it from multiple internal call sites. Fixed by monkey-patching the class's `tie_weights` (fetched via `get_class_from_dynamic_module`, the same mechanism transformers itself uses) to accept and ignore arbitrary kwargs — a single fix that resolved what initially looked like two separate errors from different call sites.
3. **Missing `ffmpeg`**: MuFun's audio loader shells out to `ffmpeg` for file decoding, not present on this box. Installed via `conda install -c conda-forge ffmpeg` into `pa1_env` (no sudo needed) — but also needed explicit `PATH=.../pa1_env/bin:$PATH` when invoking the env's Python binary directly rather than through `conda activate`, since direct binary invocation doesn't pick up the env's own `bin/` directory.
4. **Dtype mismatch, same class as the earlier Audio Flamingo 3 fix**: the internally-constructed Whisper audio tower loads its own weights via its own independent `from_pretrained` call (no dtype propagated from the outer load), landing in fp16 while the outer model runs bf16. Fixed by forcing the whole model to a single consistent dtype (float32) after loading, same resolution as AF3's earlier fix.
5. **List-vs-tensor mismatch between `generate()` and `forward()`**: `model.chat()`'s underlying `generate()` override does `images = torch.cat(images, dim=0)` if `images` is a list before proceeding, but calling `forward()` directly (needed for teacher-forced scoring, since `chat()`/`generate()` only exposes free-form output) does **not** do this conversion and assumes an already-concatenated tensor. Found by comparing the two code paths directly (line-by-line) after `forward()` raised `AttributeError: 'list' object has no attribute 'to'` on the exact same `audio_tensor` object that `generate()` had just accepted successfully. Fixed by doing the same `torch.cat` once in the shared `_build_inputs` helper.
- **Verified working end-to-end via a 3-clip known-label smoke test** before running any full evaluation, per this project's standing practice — produced sensible (if imperfect) free-form generations and teacher-forced score distributions.

**Final measured result, both tasks, validation split (teacher-forced label scoring, same methodology as every other ALM)**:

- **Clear negative result** — top1 on A is at/below the random baseline (0.167), B's is barely above it. Even the teacher-forced label scores (which don't depend on the broken free-form generation) show essentially no usable signal, consistent with CLAP's earlier failure — this and CLAP are now the two clearly-non-functional approaches tried this project, both well below every SSL-probe or other-ALM result.

### Task 1: SORD distance-aware soft labels — `src/sord_ordinal.py`
Round 4's top Task-1 recommendation, specifically framed as the CORAL fix: keep the full 6-logit head (soft-label cross-entropy against `softmax(-|rank_i - rank_true| / T)` targets) instead of CORAL's capacity-starved shared-weight-vector binary decomposition. - Best tuned plain CE (same architecture): top1=0.432, MAE=0.924.

### Contextual calibration of AF3's label scores + combined with language-ID fusion — `src/contextual_calibration.py`
Round-4 queue item 3 (Zhao et al. 2021, arXiv:2102.09690): estimate AF3's own unconditional label bias from a content-free input (near-silent noise, same prompt, 3 draws averaged), then subtract it from every real clip's label scores before softmax. **Parameter-free given the null estimate — fit against nothing from our own labels, so it cannot overfit the way the earlier weight-sweep did.**

**Results, both tasks, both prompts**:
- **B, direct prompt: top1=0.5882→0.6275, top3=0.7647→0.7941** — a large, clean win. The null-score spread for this prompt was large (~2 nats between labels), meaning AF3's `direct` prompt has a real, substantial inherent label bias that calibration successfully removes. Not quite significant on its own (p=0.29, CI=[-0.010,+0.098], but 89% of bootstrap resamples favor calibrated).
- **B, cot_then_answer prompt: 0.5588→0.5686** — small effect, consistent with a much smaller null-score spread (~0.7 nats) for this prompt — less inherent bias to correct in the first place.
- **A, direct prompt: 0.3788→0.3712** — negligible/slightly negative, consistent with an even smaller null-score spread (~0.15 nats) — essentially no fixable bias present for Task 1's `direct` prompt.
- **Pattern makes sense end to end**: calibration's benefit tracks directly with how skewed the model's own content-free label distribution is for that specific (task, prompt) pair — a good sanity check that the method is doing something real and interpretable, not adding noise.

**Combined with the round-4 language-ID fusion (the natural next step, since calibrated AF3-direct is now the strongest single Task 2 signal)**: OOF-fitted fusion of the MuQ+LangID concat probe with **calibrated** AF3-direct scores (same leakage-free methodology throughout) reaches **top1=0.6471, top3=0.8627 — a new best point estimate for Task 2, by a wide margin over every other config this project** (previous best point estimate was 0.578; note this is close to, but arrived at completely independently of, the earlier discredited validation-overfit 0.657 figure — this one went through the full leakage-free OOF pipeline with a parameter-free calibration step, not a validation-set weight sweep). Not significant vs. calibrated-AF3-alone (p=0.79, CI=[-0.049,+0.088]) — reported with the same honesty as every other point estimate this project, but this is now genuinely the strongest, best-supported combination found.

**Updated Task 2 standing**: calibrated-AF3-direct alone (0.6275) already exceeds every previously-reported Task 2 config's point estimate on its own; the full MuQ+LangID+calibrated-AF3 fusion (0.6471) is the new overall best point estimate. None of these individually clear significance against each other at n=102, consistent with the whole project's pattern, but the *sequence* of improvements (raw AF3 → calibrated AF3 → calibrated AF3 + new orthogonal language signal, OOF-fit throughout) each move the point estimate up via a distinct, well-motivated, non-overfitting mechanism.

### Task 1: production/mastering descriptors — `src/production_features.py`
Round-4 queue item 4 (loudness-war descriptors: crest factor, dynamic range, spectral tilt). **First checked the flagged confound directly** (not assumed): our own `load_audio_normalized` loudness-normalizes every clip to -23 LUFS (`TARGET_LUFS` in `src/config.py`) — absolute LUFS would carry zero signal (every clip forced to the same value). ### Statistical protocol overhaul: repeated CV + Bayesian correlated t-test — `src/bayesian_comparison.py`
Round-4 queue item 5, applied directly to this round's single highest-stakes open question: is the MuQ+LangID+calibrated-AF3 fusion (0.647 on the 102-sample validation set) actually better than calibrated-AF3 alone (0.6275), or is that a noise artifact the way the earlier 0.657 was? **Honest limitation stated up front**: no artist IDs in the manifest, so this is repeated *stratified* (not artist-*grouped*) k-fold CV on the pooled train+validation set (900 samples) — within-fold artist leakage is possible, unlike our actual artist-disjoint splits. AF3's calibrated scores are fixed/pre-computed (no per-fold leakage risk from AF3 itself, it's a zero-shot model); only the MuQ+LangID probe is refit per fold; the fusion weight (α=0.4, already OOF-fit once on the original train split) is reused as-is across all folds, since the question here is this specific frozen pipeline's evaluation variance, not re-deriving the weight each time.

- **5×5 repeated stratified k-fold (25 folds total)**: fused mean accuracy=0.5844, AF3-alone mean=0.5644 — fused's **raw mean is higher** across this larger, repeated evaluation.
- **Bayesian correlated t-test (Nadeau-Bengio variance correction, `baycomp`, ROPE=±1%)**: **P(AF3-alone better)=0.783, P(practically equivalent)=0.204, P(fused better)=0.013** — despite the higher raw mean, the corrected test leans toward favoring AF3-alone, not the fusion. The Nadeau-Bengio correction inflates the variance estimate to account for non-independence across overlapping CV folds, which is a stricter, more conservative standard than a naive mean comparison — the fused pipeline's fold-to-fold accuracy is evidently more volatile (retraining an unstable small-sample classifier each fold) than AF3's fixed, zero-shot predictions, and that instability outweighs its higher average in this test.
- **Honest conclusion, and a genuine caution about the round-4 "new best" claim**: this more rigorous protocol does **not** confirm the fusion beats calibrated-AF3-alone — if anything it leans the other way. This doesn't reverse the finding that calibrated AF3 itself is a real improvement over raw AF3 (that result has a clean, separate mechanistic explanation, the null-distribution-skew tracking), but the *specific claim* that adding MuQ+LangID fusion on top of calibration helps is now on weaker footing than the single-split bootstrap test suggested. **Recommendation for reporting**: cite contextually-calibrated AF3-alone (0.6275) as the primary Task 2 result going forward, and mention the MuQ+LangID+AF3 fusion (0.647) as an unconfirmed, and by this more rigorous test not-favored, point estimate — not as a confirmed new best.
- Full results: `results/bayesian_comparison/B_fused_vs_af3.json`.

- **Standalone (wide-deep features alone, logreg): top1=0.4091, top3=0.7803.** A real, well-above-chance signal (chance=0.167) from hand-crafted features alone, though clearly below MuQ-alone (0.508) or MERT-v2-alone (0.5455).

GridSearchCV selected the smallest C in the grid (0.001, heavy regularization) for the concatenated feature set, consistent with the model learning to lean mostly on MERT-v2's 1024 dims and only lightly on the added 98 -- a real but modest contribution, not a breakthrough.
- **Leave-one-group-out ablation on the standalone wide-deep features** (baseline top1=0.4091): removing **timbre** (68 feats: spectral shape + MFCCs) drops to 0.2652 (by far the largest drop -- timbre is the dominant contributor); removing **dynamics** (3 feats: RMS mean/std + crest factor) drops to 0.3182 (a surprisingly large drop for so few features -- reconfirms round-4's loudness-war finding from a completely different feature-extraction path); removing **pitch** (24 feats: chroma) drops to 0.3561; removing **rhythm** (3 feats: tempo/beat strength/beat-histogram ratio) drops the least, to 0.3788 -- rhythm regularity carries the weakest signal of the four groups for this task.

**Conclusion**: hand-crafted production/timbre descriptors carry genuine, measurable decade signal on their own (confirming L02's framing), and complementary information beyond what MERT-v2 already captures -- but that complementary signal shows up as a top3 gain, not a top1 gain, making this a real if modest positive rather than a new headline config. ### Round 5 item 4: Retrieval-augmented ICL with AF3 — feasibility check, negative
Item 4's own stated scope explicitly required "a feasibility check first (does AF3's processor accept multi-audio conversation turns)" before building the retrieval pipeline (MuQ-kNN exemplars prepended before the query). Ran that check directly rather than assuming either way:
1. `processor.apply_chat_template()` on a conversation with 3 `{"type": "audio"}` blocks interleaved with text collapses all three into a **single** `<sound>` placeholder token in the rendered text, silently dropping the interleaved structure (each text segment gets concatenated together, audio positions are not preserved).
2. Calling `processor(text=..., audio=[3 arrays], ...)` on that same template raises `ValueError: Got 1 text but 3 audios; they must match 1:1` -- the processor hard-enforces a 1:1 text:audio ratio at the API level.

**Conclusion: infeasible through the standard/documented interface.** AF3's processor and chat template are built for exactly one audio clip per conversation turn; forcing multiple would require manually reconstructing the tokenization and feature-concatenation logic in a way the underlying model (AF-Whisper audio tower + Qwen2 LLM) was almost certainly never trained to handle, making any result from such a hack uninterpretable even if it could be forced to run. Not pursuing further per the item's own stated conditional logic -- this is a genuinely-tested infeasibility, not a presumed/skipped one.

### Round 5 item 7: PupuM2D-Large frozen probe + OOF fusion — `src/pupum2d_features.py`, `src/encoder_fusion_oof.py`
Round-5's TODO item names this "PupuJEPA-Large" -- the source doc (`round5_lecture_grounded_research.md`) itself flagged a naming ambiguity ("L02b slide 27 links github.com/sizigi/PupuM2D; the repo cited in the paper's BibTeX is sizigi/PupuJEPA -- use that"). Verified before touching anything: `arxiv.org/abs/2606.25713` is real ("Frequency-Aware Self-Supervised Music Representation Learning", Gu et al. 2026); the actual maintained repo is `sizigi/PupuM2D` (`sizigi/PupuJEPA` doesn't exist as a separate repo), and its own model module is literally named `model/pupujepa.py` -- both names point at the same thing, `PupuM2D` is the correct one to use. A JEPA-family SSL model (predicts latent embeddings of masked 2D spectrogram patches with an EMA target encoder) -- genuinely different pretraining family from every encoder tried this project (MERT/MuQ/MusicFM/CultureMERT are all 1D masked-token prediction), proposed specifically as a decorrelated-error fusion source, independent of its own standalone accuracy.

**No official inference/feature-extraction script ships with the repo** (training-code-only release, confirmed by listing the full repo tree). Reimplemented the minimum needed for a frozen embedding myself, sourcing every constant directly from the authors' own `train_pupum2d.py` (`extract_mel_features`, including its hardcoded log-mel normalization constants) and `model/pupujepa.py` (patch_embed + EMA teacher encoder, no masking/predictor at inference -- the standard I-JEPA/A-JEPA linear-probe eval convention) -- not guessed. Three real integration bugs found and fixed, each verified against the checkpoint/source rather than assumed:
1. `model/__init__.py` in the upstream repo does `from .pupum2d import *`, a stale module name -- the actual file is `model/pupujepa.py` (leftover rename artifact). Patched our local clone's `__init__.py` (one line) to import the right module.
2. `args.json` declares `qk_norm: true`, but the released `model.safetensors` has **no** `q_norm`/`k_norm` weights at all for any attention block (checked directly against the safetensors key list before assuming). Forced `qk_norm=False` when constructing the model, trusting the checkpoint's actual saved parameters over the (likely timm-version-drifted) config flag -- `strict=True` state_dict load then succeeds cleanly with zero missing/unexpected keys.
3. The original `forward()` always narrows `rope_encoder.get_embed(grid_size)` via fancy-indexing with a `(B, N_subset)` mask-index tensor before passing it to a block -- passing the raw, un-indexed rope tensor for the full (unmasked) inference case caused a shape mismatch inside `timm`'s `apply_rot_embed_cat`. Fixed by constructing a "full" index (`arange` over all patches, expanded to batch size) and indexing the same way the authors do for their masked subsets.

**Verification before trusting the pipeline**: after each fix, ran a 4-clip smoke test and checked pairwise embedding cosine similarity (0.68-0.79, non-degenerate, no NaNs, distinct per-clip norms ~40-42) before committing to the full extraction -- same positive-control practice used for CLaMP3 and every other new pipeline this project.

Full extraction (1290/1290 A, 1002/1002 B) + classifier/PCA ablation (single global mean-pooled embedding, no layer structure):
- **A: logreg, PCA128 — top1=0.5152, top3=0.8485.** Slightly above MuQ-alone (0.508), below MERT-v2-alone (0.5455).
- **B: logreg, no PCA — top1=0.4804, top3=0.8235.** Below MuQ-alone (0.500) — the weakest standalone Task 2 config among the encoders tried this project (below CLaMP3's 0.5098).

**OOF fusion with MERT-v2-30s** (`src/encoder_fusion_oof.py`, new generic two-encoder version of this project's standard leakage-free OOF fusion methodology -- fit weight on 5-fold OOF train predictions, freeze, apply once to validation):
- **A: accuracy-optimal fusion (α=0.6 MERT-v2 / 0.4 PupuM2D) reaches top1=0.5606** — the **best Task 1 point estimate found this entire project**, a further lift over MERT-v2-alone (0.5455). Not significant vs. either alone (p=0.69 vs MERT-v2-alone, p=0.31 vs PupuM2D-alone, n=132), the now-familiar pattern, but a genuinely new best point estimate and PupuM2D's decorrelated-error hypothesis showing real (if unconfirmed) signal.
- **B: the OOF fit collapses the fusion weight to α=1.0 (100% MERT-v2, 0% PupuM2D)** for both the NLL-optimal and accuracy-optimal objectives -- the fusion procedure itself correctly determined PupuM2D contributes nothing useful for Task 2, rather than needing us to eyeball a weak result. Fused == MERT-v2-alone exactly (0.6471); significantly beats PupuM2D-alone (p=0.0019) simply because MERT-v2 dominates, not informative about fusion value.

Minor note for future reproducibility: `pupum2d_large_alone`'s B number in the fusion script's own output (0.4608) differs slightly from the standalone ablation's reported best (0.4804) -- traced to `encoder_fusion_oof.py`'s `fit_probe` using plain `GridSearchCV(cv=5)` (unshuffled default splitter) vs. `train_probe.py`'s explicit `StratifiedKFold(shuffle=True, random_state=0)`, which selects a different best `C` during the grid search. Both are legitimate CV splits: this doesn't affect the fusion conclusion (PupuM2D trails MERT-v2 by a wide margin either way, and the OOF-fit weight already independently collapsed to zero), but is worth aligning if `encoder_fusion_oof.py` is reused for closer future comparisons.

**Conclusion**: PupuM2D-Large is a genuine negative as a standalone encoder for both tasks, but round-5's fusion-diversity hypothesis (item 7's actual stated purpose) shows a real, if not-yet-significant, positive for Task 1 specifically -- worth keeping as a candidate for the current Task 1 recommended config, while Task 2 gets no benefit from it. Full results: `results/pupum2d_large_ablation_summary_{A,B}.json`, `results/encoder_fusion_oof/{A,B}_mertv2_30s_x_pupum2d_large.json`.

### LoRA fine-tune of MERT (`src/finetune_lora.py`) — testing IMPROVEMENT_FINDINGS.md's PETL-paper-informed recipe
- **Config**: MERT-v1-330M encoder frozen except LoRA adapters (peft 0.21.0) on `q_proj/k_proj/v_proj/out_proj` of the **top 8 of 24 encoder layers** (layers 16-23), rank=8, alpha=16, dropout=0.05 — 530,438 trainable params out of 315,959,430 total (0.17%), verified via a forward+backward smoke test before committing to a full run. Classification head fully trainable (randomly initialized, no pretrained weights). lr=1e-4 (higher than the 2e-5 used for full fine-tune, appropriate for a much smaller trainable surface), AdamW, cosine schedule, 15 epochs, batch=4, 10s crops (same as full fine-tune). Two augmentations added that the full-fine-tune runs never used: waveform-domain time masking (our stated analogue of SpecAugment — MERT takes raw waveform, not a precomputed spectrogram, so this masks contiguous waveform spans, up to 8% length, 2 masks/clip, rather than literal time/frequency spectrogram bins) and waveform mixup (beta(0.2,0.2) interpolation + soft-label KL loss).
- **Task B, first run (LoRA + time-mask + mixup)**: loss decreased monotonically every epoch (1.798→1.566) but **never got close to competitive** — best_val_top1=**0.3235** (epoch 8+, plateaued), well below every other config tried for B (frozen MERT 0.471, full fine-tuned MERT 0.412, MuQ 0.500, MuQ+AF3 fusion 0.657). Loss curve was still decreasing at epoch 14 with no plateau in the loss itself (though val_top1 did plateau from epoch 8 on) — ambiguous whether this needs more epochs or whether the combination of a very small trainable surface (0.17%) with aggressive augmentation (mixup soft-labels + waveform masking) is simply too hard a training signal to converge quickly. Not concluding "LoRA doesn't work" from this alone — ablating the augmentation next, per standing no-premature-conclusions practice, before drawing that conclusion.
- **Ablation 1 (no-aug, 15 epochs)**: `--no-time-mask --no-mixup`, otherwise identical — `results/mert_lora_B_noaug/`. best_val_top1=**0.3627** — removing augmentation helped (+3.9pt over the augmented run), confirming augmentation was part of the problem, but still far below every competing config.
- **Ablation 2 (no-aug, 40 epochs, checking convergence)**: same no-aug config, 40 epochs instead of 15 — `results/mert_lora_B_noaug_40ep/`. Loss kept decreasing the whole way (1.59→0.90) but val_top1 clearly decelerated and plateaued in the 0.33-0.38 range from epoch ~20 onward (epoch 20: 0.353, epoch 30: 0.343, epoch 39: 0.333, best overall 0.3824 at one epoch in between) — **not a still-converging run cut short, a genuine plateau**, confirmed by running 2.7x longer than the original 15 epochs and gaining only +2pt top1 for it while train loss nearly halved (classic overfitting-to-train-loss-without-val-gain signature).
- **Conclusion (measured, not presumed)**: LoRA fine-tuning of MERT (rank 8, top-8-layers, q/k/v/out_proj, 0.17% trainable params) **does not close the gap for Task B at this data scale** — best achieved 0.382, well below frozen MERT probe (0.471), frozen MuQ probe (0.500), and nowhere near the MuQ+AF3 fusion result (0.657). This is a real, measured discrepancy with Huang et al.'s (arXiv:2411.19371) GTZAN finding that LoRA(rank 2) beat full fine-tune and nearly matched the frozen probe (74.7% vs 75.6%) — worth reporting honestly in the write-up as a task/dataset-regime difference rather than a contradiction of their result: GTZAN is a much larger, acoustically-grounded genre task, while Task B is our smallest-n, most editorial/non-acoustic label (per the confusion-diagnostic and literature discussion above) — plausibly the hardest possible case for any encoder-adaptation method, LoRA included, consistent with this project's now-repeated finding that Task B specifically resists nearly every technique except a differently-pretrained encoder (MuQ) and probability-level fusion (AF3). Not testing further LoRA hyperparameters (rank/layer-count/lr grid) given this plateau evidence and the much larger gap to already-established strong configs — deprioritizing further LoRA tuning in favor of the remaining lower-priority queue items.
- **Task A**: not run — given Task B's clear negative/plateaued result and the added evidence that Task A's configs are already statistically indistinguishable from each other (see significance section above), a LoRA run for A is deprioritized rather than skipped on presumption; can be picked up if time allows.
